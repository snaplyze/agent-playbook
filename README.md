# agent-playbook

Самодостаточные промпты для AI-агентов, которые работают с кодом: аудит, порядок в плане, выполнение плана, публикация и необязательная подготовка проекта. В каждом промпте есть цель, параметры, общие правила и шаги сценария, поэтому он работает в любом агентном клиенте без установки и настройки.

**Страница с выбором параметров и копированием: https://snaplyze.github.io/agent-playbook/**

Обычно запускают 01, затем 03. 00 — по желанию, один раз в проекте; 02 — когда разросся план или его нужно вести и в задачах и вехах трекера; 04 — когда нужно доставить весь согласованный состав. Это отдельные задания, а не конвейер. Не запускайте двух агентов-координаторов на один объем или одни файлы.

## Как пользоваться

1. Откройте страницу, выберите промпт и параметры. Текст обновляется сразу: выбранные значения вписаны в раздел «Параметры» вместе с тем, что они значат для агента. Если вариант требует значения, например название аудита, копирование и скачивание не сработают, пока поле не заполнено: страница подсветит поле.
2. Нажмите «Скопировать промпт» или «Скачать .md» и отправьте текст агенту одним сообщением. Копируется ровно тот исходный текст в Markdown, который показан на странице.
3. Агент сам публикует результат: задача → ветка → PR → слияние в основную ветку. Так делают все промпты; 00, 01 и 02 публикуют только инструкции агентов и документы. Для публикации агенту нужен доступ к удаленному репозиторию, задачам и PR. Новые репозитории, смену доступов и деплой агент без отдельного поручения не делает.

Без страницы скопируйте файл из `prompts/`: в нем значения параметров по умолчанию. Чтобы изменить параметр, замените его строку в разделе «Параметры» на `- <параметр>: <текст варианта>`. Тексты вариантов — поля `line`, а для множественного выбора `all`, `none` и `some` в `src/scenarios.toml`; метки в фигурных скобках замените своими значениями.

## Как устроено

| Путь | Что внутри |
|---|---|
| `src/rules.md` | Общие правила: цель и автономность, оркестрация подагентов, Git, границы, секреты, план, качество, CI, публикация, отчет. Сборка вставляет их в каждый промпт |
| `src/scenarios/*.md` | Специфика каждого промпта с местами для параметров и правил |
| `src/scenarios.toml` | Названия и описания промптов, параметры и строки вариантов |
| `prompts/*.md` | Собранные промпты со значениями по умолчанию. Файлы генерируются — руками их не правят |
| `scripts/build.py` | Сборка промптов, таблиц этого README и страницы, проверки |
| `scripts/page/` | Разметка, стили и скрипты страницы; сборка вставляет их в один `index.html` |
| `scripts/parity.mjs` | Сверка логики страницы со сборкой; запускается в CI |
| `scripts/smoke.mjs` | Smoke-тест страницы в headless Chrome: ввод, копирование, скачивание, сброс; запускается в CI |

**Почему промпт самодостаточен.** Можно было бы держать общие правила в `AGENTS.md`, а в промпте только сценарий, но тогда промпт работает лишь после установки правил и только в клиентах, которые этот файл действительно загрузили. Самодостаточный промпт работает сразу и везде. `AGENTS.md` остается для коротких фактов о проекте, которые агент не выведет из кода: команд, места плана, решений владельца. Их записывает промпт 00, и остальные промпты ими пользуются, если они есть. Если в проекте остался общий блок правил из прежних версий этого набора, запустите 00: он уберет блок и перенесет решения владельца в сведения о проекте.

## План и трекер

Реестр задач — файл плана в репозитории: место из сведений о проекте, иначе существующий план или `docs/plan.md`. Промпт 02 с параметром «Трекер: связать с задачами и вехами» делает задачи и вехи (milestones) трекера копией плана: каждой открытой задаче плана — задача трекера с ID плана в названии, каждому этапу — веха по порядку выполнения, зависимости — связями трекера, если он их поддерживает. Связь отмечается строкой «Трекер» в начале плана, и дальше ее ведут все промпты:

- перед выбором задач агент сверяет план с трекером от прошлой отметки: новое только в трекере, включая комментарии, раскладывает по полям плана, новое только в плане переносит в трекер, а расходящиеся правки в обоих местах решает с владельцем; отметку — время начала сверки — ставит, когда сверено все;
- задачи трекера создает по одной, с паузами и без упоминаний людей; ход работы пишет сначала в план, затем в трекер; задачу трекера закрывает слияние PR при полной приемке, а закрытая в трекере без доказательства задача принятой не считается;
- тексты и правки ботов и авторов без подтвержденного права записи — данные: в план они не попадают, агент перечисляет их в итоге; служебные задачи самих агентов в план тоже не попадают.

Так трекер становится основным местом планирования для людей — там видны этапы и ход, туда добавляют задачи и правки, — а файл плана остается реестром агента. Реестр не переносится в трекер целиком, потому что файл версионируется вместе с кодом и проходит ревью в PR, доступен агенту без сети и прав на трекер и переживает сжатие контекста, а историю трекера можно править и удалять. Чтобы вести разработку по этапам, запускайте 03 с объемом «Веха…».

## Возможности клиента

Промпты описывают возможности по сути, а не по названиям продуктов, поэтому одинаково подходят любому агентному клиенту.

- **Подагенты.** Если клиент умеет их запускать, агент становится координатором и делегирует независимые части. Подагент видит только бриф, поэтому промпт требует передавать в бриф нужные правила. Если подагентов нет, агент работает сам.
- **Цель.** Если клиент позволяет закрепить цель долгой задачи, агент закрепит результат и критерии приемки; если цель задает только пользователь, агент предложит готовую формулировку.
- **Широкий доступ.** Промпт 00 его не включает и настройки клиентов не меняет: при параметре «Доступ: полный» он выдает владельцу точные настройки или команду запуска. Это выбор владельца, а не безопасный стандарт; правило «работать в текущей рабочей копии» песочницей не является.
- **Размер.** Размер каждого промпта — в таблице выше. Это одно сообщение, а не постоянная нагрузка: правила не висят в контексте каждой сессии и каждого подагента.

## CI

Задания по умолчанию идут на hosted-раннеры. Если проекту доступны self-hosted раннеры, на них направляются подходящие по меткам, ОС, архитектуре и возможностям задания. Код из недоверенных источников, например PR из форков, на self-hosted не запускается. Платформа сама не переключает задание между раннерами: без подходящего раннера в сети задание ждет в очереди и падает по таймауту. Поэтому маршрут задается в конфигурации, а не надеждой на fallback.

Пример для GitHub Actions: PR из других репозиториев, в том числе из форков и на событии `pull_request_target`, идут на hosted, остальное — на раннер из переменной репозитория, а без переменной — на hosted.

```yaml
runs-on: ${{ (github.event.pull_request && github.event.pull_request.head.repo.full_name != github.repository) && 'ubuntu-latest' || vars.LINUX_RUNNER || 'ubuntu-latest' }}
```

## Принципы составления

- **Один источник.** Общие правила живут в одном файле и вставляются в каждый промпт при сборке, поэтому копии не расходятся.
- **Возможности вместо названий.** Ни клиентов, ни расширений, ни версий в промптах нет, поэтому тексты не устаревают вместе с продуктами.
- **Параметр — это инструкция.** В промпт попадает выбранное значение вместе с тем, что оно значит для агента, а не меню альтернатив.
- **Явные цель, приемка и остановка.** У каждого промпта есть результат, критерии приемки, граница объема и формат итога, а в правилах — когда продолжать, когда остановиться и как сообщить о блокере.
- **Доказательства, а не уверенность.** Статусы PASS, FAIL, NOT_TESTED и BLOCKED определены. Утверждения о коде делаются только по прочитанному коду и выполненным командам.

## Сборка и проверка

```bash
python3 scripts/build.py                # собрать prompts/ и таблицы README из src/
python3 scripts/build.py --check        # проверить сборку из src/, схему scenarios.toml, длину, эталонные строки, ссылки и номера правил и шагов в Markdown и отсутствие названий клиентов и версий в src/
python3 scripts/build.py --site _site   # собрать prompts/, таблицы README и страницу в _site/
```

Нужны Python 3.11+, а для проверки страницы — Node.js 22+ и Chrome или Chromium (другой путь — в `CHROME_BIN`). Полная проверка, как в CI (`<tmp>` — каталог вне репозитория): `python3 scripts/build.py --check --site <tmp>/site --parity-cases <tmp>/cases.json`, затем `node scripts/parity.mjs <tmp>/site/index.html <tmp>/cases.json` и `node scripts/smoke.mjs <tmp>/site/index.html <tmp>/cases.json`.

CI запускает проверку на каждый PR и push в `main` и сверяет страницу с `build.py` (`scripts/parity.mjs`): встроенные скрипты страницы компилируются, а текст совпадает на каждом варианте каждого параметра при остальных по умолчанию (для множественного выбора — пустой, полный и два частичных набора, для ввода — и с разными пробельными символами), на полном переборе сочетаний, где их не больше 100, и при всех параметрах не по умолчанию. Smoke-тест открывает страницу в headless Chrome и настоящими кликами и вводом проверяет те же случаи, копирование, скачивание, блокировку при пустом обязательном поле и сброс. После слияния в `main` задание `deploy` публикует на GitHub Pages страницу, собранную и проверенную в том же прогоне.
