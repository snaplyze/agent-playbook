# agent-playbook

Готовые сценарии для AI-агентов, которые работают с кодом, и общий контракт правил для `AGENTS.md`. Тексты не привязаны к конкретному клиенту: они рассчитаны на любого агента, который читает файл инструкций проекта и запускает команды, а при возможности и подагентов.

Страница с выбором сценария, полями параметров и копированием: **https://snaplyze.github.io/agent-playbook/**

## Как устроено

- **Общий контракт агента** — постоянные правила: цель и автономность, оркестрация, Git, границы изменений, секреты, план, качество, CI, публикация, отчет. Блок стоит в начале корневого `AGENTS.md` проекта, и клиент загружает его в каждую сессию.
- **Сценарии** — разовые поручения. В каждом только его специфика и страховочный минимум на случай, если контракта в проекте еще нет.

| № | Сценарий | Когда | Результат | Чего не делает |
|---|---|---|---|---|
| 00 | [Подключение](prompts/00-setup.md) | Первое подключение проекта или обновление контракта | Контракт в `AGENTS.md`, раздел «Контракт проекта», подтвержденная загрузка в каждом клиенте | Не трогает продукт, CI и план |
| 01 | [Аудит](prompts/01-audit.md) | Нужна проверка состояния и очередь исправлений | Находки с доказательствами, приоритетом, решением и приемкой — прямо в плане | Не меняет код, тесты и CI |
| 02 | [Порядок в плане](prompts/02-plan.md) | План раздут, статусы расходятся, агент зацикливается | Компактный реестр, цельные задачи с приемкой | Не выдает правку плана за ускорение продукта |
| 03 | [Выполнение](prompts/03-execute.md) | Довести до результата весь план, один аудит или список ID | Каждый ID проверен и слит в основную ветку или назван конкретный остаток | Не придумывает новый объем и не полирует после приемки |
| 04 | [Публикация](prompts/04-publish.md) | Первый импорт или полная сверка с удаленным репозиторием | Доказанная полнота доставленного состава в основной ветке | Не оптимизирует продукт и не переносит хостинг |

## Как запускать

1. Один раз в проекте отправьте агенту **00 · Подключение**: весь файл одним сообщением.
2. Дальше отправляйте нужный сценарий так же, одним сообщением. Параметры пишите отдельными строками перед текстом сценария:

   ```text
   Объем: аудит 2026-10-13
   <текст prompts/03-execute.md>
   ```

Обычный порядок: 00, затем 01 → 03, чтобы найти и исправить проблемы. 02 нужен, когда разросся план, 04 — когда нужно доставить весь согласованный состав. Это отдельные поручения, а не конвейер. Не запускайте двух координаторов на один объем или одни файлы.

| Сценарий | Параметр | Значение |
|---|---|---|
| 00 | `CI: …` | Решение владельца о раннерах, важнее обнаруженного: `только hosted`, `self-hosted для всех подходящих заданий` или свое правило |
| 00 | `Доступ: полный` | Разрешить широкий неинтерактивный доступ агента на уровне проекта |
| 00 | `Установить оркестрацию: …` | Источник ролей или расширения для подагентов и область установки: `проект` или `пользователь` |
| 03 | `Объем: …` | `весь план` (по умолчанию), `аудит <название>` или список ID |
| 04 | `Разрешено: …` | Действия сверх обычных через запятую: `создание репозитория`, `первичная загрузка`, `смена видимости` и другие из сценария |

## Совместимость

Контракт описывает возможности по сути, а не по названиям продуктов. Как именно включить каждую возможность в конкретном клиенте, агент выясняет сам по документации клиента в сценарии 00.

- **Файл инструкций.** `AGENTS.md` — открытый формат, который большинство агентных клиентов читает без настройки. Если клиент читает только собственный файл, сценарий 00 добавит в этот файл одну строку импорта, не копируя правила. Файлы, которые у других клиентов перекрывают `AGENTS.md`, сценарий не создает.
- **Подагенты.** Если клиент умеет их запускать, агент становится координатором и делегирует независимые части. Бриф делается самодостаточным: подагент может не видеть ни `AGENTS.md`, ни диалог. Если подагентов нет, агент работает сам.
- **Цель.** Если клиент позволяет закрепить цель или план, агент закрепит результат и критерии приемки. Если цель задает только пользователь, агент предложит готовую формулировку.
- **Широкий доступ.** Настраивается только по явному параметру владельца. Это выбор владельца, а не безопасный стандарт; правило «работать в текущей рабочей копии» песочницей не является.
- **Размер.** Блок контракта занимает около 10 тыс. символов, это примерно 17,5 КБ: кириллица в UTF-8 занимает 2 байта на символ. Часть клиентов молча обрезает длинные инструкции, у некоторых предел — 32 КиБ на все файлы инструкций. Поэтому блок стоит в начале `AGENTS.md` и заканчивается видимой строкой «Конец общего контракта агента», по которой агент замечает обрезку.

## CI

Задания по умолчанию идут на hosted-раннеры. Если проекту доступны self-hosted раннеры, на них направляются подходящие по меткам, ОС, архитектуре и возможностям задания. Код из недоверенных источников, например PR из форков, на self-hosted не запускается. Платформа сама не переключает задание между раннерами: без подходящего раннера в сети задание ждет в очереди и падает по таймауту. Поэтому маршрут задается в конфигурации, а не надеждой на fallback.

Пример для GitHub Actions: PR из форков идут на hosted, остальное — на раннер из переменной репозитория, а без переменной — на hosted.

```yaml
runs-on: ${{ (github.event_name == 'pull_request' && github.event.pull_request.head.repo.fork) && 'ubuntu-latest' || vars.LINUX_RUNNER || 'ubuntu-latest' }}
```

## Принципы составления

- **Одно правило — одно место.** Общее живет в контракте, специфика — в сценарии. Сценарий повторяет только страховочный минимум, и этот раздел «Основа» во всех сценариях одинаков дословно.
- **Возможности вместо названий.** Ни клиентов, ни расширений, ни версий в промптах нет, поэтому тексты не устаревают вместе с продуктами.
- **Явные цель, приемка и остановка.** У каждого сценария есть результат, критерии приемки, граница объема и формат итога, а у контракта — правила, когда продолжать, когда остановиться и как сообщить о блокере.
- **Доказательства, а не уверенность.** Статусы PASS, FAIL, NOT_TESTED и BLOCKED определены. Утверждения о коде делаются только по прочитанному коду и выполненным командам.
- **Простота решения.** Сначала убирается лишняя работа, потом добавляются кеш и параллелизм. Вытесненное удаляется в той же задаче.

## Проверка

```bash
python3 scripts/check.py
```

Скрипт проверяет, что в промптах нет названий клиентов, расширений и версий; что раздел «Основа» во всех сценариях совпадает дословно; что блок контракта ровно один, начинается заголовком, заканчивается строкой «Конец общего контракта агента» и укладывается в 18 КиБ; что ссылки в README и `AGENTS.md` рабочие. Тот же скрипт запускается в CI на каждый PR и push в `main`.

Страницу собирает `scripts/build_site.py` из `prompts/` и таблиц этого README: сценарии, их описания и параметры берутся отсюда, поэтому страница не расходится с файлами. После слияния в `main` workflow `pages` публикует ее на GitHub Pages. Локальная сборка: `python3 scripts/build_site.py --out _site`.
