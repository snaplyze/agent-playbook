# Выполнение плана

Автономно доведи объем плана из параметра «Объем» до проверенного результата и слияния в основную ветку, с доказательствами по каждому ID. Исполняй сам или через исполнителей: не подменяй исполнение новым промптом и не проси владельца запустить работу вручную.

## Границы
- Меняется то, что нужно задачам плана из объема: код, тесты, документы, затронутые конфигурации CI. Разрешены нужные инструменты, зависимости через штатный менеджер с lockfile и изолированные тестовые сервисы.
- Неудачный компонент в рамках результата разрешено заменить целиком, даже если diff большой; новые функции и правки незатронутого — нет.
- Повторный полный аудит, общая уборка, настройка агентов и задачи плана вне объема сюда не входят. Второго координатора на тот же объем не запускай.

## Подготовка
1. Прочитай требования, реестр и текущую запись. Принятое не переделывай, но проверь, не изменились ли его предпосылки. Для объема «весь план» при отсутствии плана составь компактный по требованиям.
2. Зафиксируй конечный объем: оставшиеся ID, зависимости, приемку. Внешний отчет аудита при необходимости перенеси в реестр один раз. Гипотезу сначала подтверди; невозможность проверки — не опровержение. Низкий приоритет не исключает ID, отсрочки владельца сохраняются. Производительность на ожидаемой нагрузке и отсутствие лишних слоев — часть качества; необязательные идеи обязательствами не становятся.
3. Перед правкой компонента уточни контракт и инварианты, причину затрат, нагрузку, решение, что удаляется, функциональную и ресурсную приемку. Общую причину устраняй один раз и проверяй все связанные с ней ID.
4. Ближайшие задачи плана детализируй, дальние держи компактно; упорядоченный план не перестраивай. Независимые потоки отдавай исполнителям с явным владением файлами, ревью добавляй по риску, зависимые правки делай последовательно. В брифах прямо пиши: нужно цельное решение причины, а не минимальный diff.

## Цикл задачи плана
Контракт и причина → цельное изменение → проверка поведения и ресурсов → удаление вытесненного → запись в плане → следующая задача плана. Опустевшую очередь пополняй из реестра.
- Индекс, пакетная или потоковая обработка — по контракту компонента, с учетом подготовки, памяти и объема результата; микрооптимизация поиска не заменяет устранения полного сканирования. Кеш, параллелизм и fallback — только при доказанной пользе, с ключами, инвалидацией, лимитом памяти и обработкой ошибок. Два алгоритма или старый и новый путь в production — только с владельцем перехода и условием удаления; наивная эталонная реализация для сравнения живет только в тестах.
- Спорные API, версии и флаги зависимостей сверяй с официальной документацией или исходником.
- Перед рискованной заменой зафиксируй поведение на границе модуля, API или CLI; старый дефект при этом требованием не становится. Для дефекта нужен воспроизводимый сигнал. Расширяй существующие тесты параметризацией, новый тестовый фреймворк вводи только при необходимости, общие изменяемые fixtures изолируй. Не закрепляй число внутренних вызовов, имена helpers и жесткие пороги времени: ресурсная граница ограничивает значимую работу — запросы, рост работы, — а не маршрут исполнения.
- Для тяжелого пути возьми цель из требований или нагрузки и сравни до и после на тех же данных и в той же среде: холодный и прогретый путь, несколько размеров, повторы. Очевидное локальное упрощение большого бенчмарка не требует. Компромисс, например «быстрее, но больше памяти», называй компромиссом.
- Переиспользуй результат проверки только при тех же входах и среде; UI проверяй в работающем сценарии. Неудачный вариант не наращивай — пересмотри модель. Итог блока: сохраненный контракт, замененное и удаленное, измеренный эффект или причина отсутствия замеров.
- Если задаче плана нужны credentials, подготовь игнорируемый файл-шаблон или место в хранилище (путь, формат, права, способ проверки), не затирая существующих значений. Когда значения понадобятся, попроси владельца внести их в подготовленный файл или хранилище, а не присылать в чат; полученные проверь, не раскрывая. Независимое продолжай.
- Предпосылкой доставки считай только запуск недоверенного кода на self-hosted и нарушение решения владельца о CI в затронутых конфигурациях: исправь их до публикации. Остальные расхождения с правилами CI, например hosted вместо возможного self-hosted, доставку не блокируют: исправь их, когда нужный раннер доступен, иначе оставь маршрут и запиши расхождение задачей плана. Проверки не удаляй и ОС механически не меняй.

## Приемка
- Каждый ID объема: реализован и слит; уже устранен, неприменим или опровергнут — с доказательством; либо назван конкретный остаток с причиной. Отмена владельцем — не реализация, запись в плане — не исправление, NOT_TESTED — не PASS.
- Проверены обязательные результаты и сквозные сценарии; заглушки и локальные тесты вместо требуемой интеграции — не готовность.
- Документация, команды и ссылки соответствуют изменениям.
- Изменения слиты в основную ветку.

## Когда остановиться
- Остановись, когда выполнена приемка всего объема. Создание PR, первый этап, MVP или пустая видимая очередь объем не завершают, пока в реестре остаются его задачи плана.
- Перед финалом сверь весь объем; внутренний тупик устрани сам.

## Итог
Сделанное, проверки с уровнем доказательства, ID, задачи в трекере, PR и SHA, остаток и нужные действия владельца.
